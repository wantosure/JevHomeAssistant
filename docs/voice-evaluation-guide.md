# 静默语音助手：测试集建设与评分办法

版本：1.0 · 2026-09-27。适用当前“安卓本地 VAD/ASR、App 直连 Jev、无唤醒词”方案。样例数据见 [初始样例](../testdata/voice-cases-starter.jsonl)，设备 ID 见 [设备协议](device-control-contract.md)。

## 1. 先确定要回答的三个问题

1. **该不该介入？** 日常对话、电视声、复述或半句话有多少被误判成指令？真正的指令有多少被忽略？
2. **介入后判得对吗？** 家居/闹钟/电脑类别，设备或设备组、动作和参数是否全对？
3. **整条语音链路可靠吗？** 麦克风、VAD、ASR、Jev、规则校验和执行各自造成了多少错误？

把单条指令的准确率和“每小时误执行次数”分开报告。无唤醒词产品的自然环境绝大多数是非指令，只有指令准确率会掩盖误触发。

## 2. 三类互补测试集

| 集合 | 单位 | 内容 | 用途 |
| --- | --- | --- | --- |
| 标注语句集 | 一句完整话语及其上下文 | 人工转写、音频文件、期望业务和动作 | 稳定复测 Jev、ASR 与端到端结果 |
| [ASR 误识别测试集](asr-misrecognition-cases.md) | 原始命令及其模拟 ASR 错误文本 | 同音/近音转写偏差，预期动作关联原始用例 ID | 单独验证错误转写进入 Jev 后能否恢复原指令 |
| 连续环境集 | 保留原始时间轴的长录音 | 安静、聊天、电视、多人、真实指令；逐段标注 | 测 VAD 漏检、分段错误和每小时误触发 |

前者应包含真实人声录制，不应只用 AI 批量生成文字。后者必须保持自然指令比例和说话频率，不能为了凑样本每 10 秒插入一条指令。

## 3. 标准答案如何标

每条样本先由人确定说话内容和上下文，再标结果。以下字段是评测格式，和 Jev API 字段不同。

| 字段 | 含义 |
| --- | --- |
| `id` | 永不复用的样本 ID |
| `split` | `dev` 调参、`test` 封存；按录制人/场次分组 |
| `audio_path` | 相对路径；纯文字起步时为 `null` |
| `reference_text` | 人工校对的完整原话，不是 ASR 输出 |
| `asr_text` | 评测运行时产生，标准集可空 |
| `context` | App 在实际运行时确实可获得的默认房间、时间、上一条已接受指令等；评测程序将它传入判断 |
| `recording_meta` | 标注者知道的说话来源、距离、电视声等；仅用于分组统计，不传给 Jev |
| `expected.decision` | `execute`、`ignore` 或 `needs_input` |
| `expected.intent` | 家居、闹钟、电脑、闲聊、其他；即使不执行也可标候选业务 |
| `expected.operations` | 期望目标/动作/参数列表；不执行时为空 |
| `tags` | 复述、否定、方言、电视声、近音设备名等难点 |

`needs_input` 表示确实是向助手发请求，但缺必要信息；它应在页面说明原因，不产生设备副作用。`ignore` 表示不应介入。若仅听文字无法判断是不是对助手说，例如有人对家人说出完全相同的“把灯关了”，标 `ambiguous_addressee` 并单列统计；不要硬将其塞进一个确定标签，然后声称模型一定能解决。

**严禁把 `recording_meta.source` 当成模型输入。** 它是评测时的真实来源标签，实际 App 没有这个信息。样例中的 `context` 也只含实际可获得字段；新加字段时逐项审查，避免把答案泄漏给模型。

闹钟相对时间必须给固定基准时间和时区，例如 `2026-09-27T20:00:00+08:00`；否则“明天七点”的正确答案会随运行日期改变。设备组的标准答案必须是**完整展开后的 ID 集合**，不能只写“所有灯”。

两人独立标注高风险、歧义和误触发样本；不一致时回听音频并写一条裁定原因。标注者在形成标准答案前不看 Jev 预测。保留“无法可靠标注”状态，不强行制造标准答案。

## 4. 样本怎么收

建议第一轮目标为 **约 500 条短语音 + 至少 8 小时连续环境音**；这是建设目标，不是统计可靠性的保证。短语音可先按下表覆盖，后续按失败类型补样：

| 类别 | 初始数量 | 必含情况 |
| --- | ---: | --- |
| 明确家居指令 | 150 | 每个常用房间、单设备/组、开关/数值、口语别名 |
| 明确闹钟 | 60 | 明天、今天、每日、修改、取消、时区与早晚歧义 |
| 明确电脑控制 | 40 | 音量 0/100、媒体、白名单应用、电脑离线 |
| 普通闲聊/无关话语 | 100 | 家人聊天、自言自语、背景故事和未支持任务 |
| 高相似负例/拒绝执行 | 150 | 复述、引用、否定、条件句、电视声、指代不明、冲突/越界、半句 |

同一语义用不同人、距离、音量、口音和自然措辞录制，但不能让一人连读 20 个仅替换设备名的模板充当独立样本。固定手机实际摆位，分近距离/远距离/背对手机；记录电视开关、噪声、说话人数、录音设备型号与系统版本。真实设备动作先以 observe 模式跑。

连续环境集至少覆盖：家中无人安静、电视/音箱、家人交谈、厨房/风扇噪声、真实指令穿插和多人重叠。统计总小时数、人工标出的有效指令数和误触发数。录到他人谈话时先让参与者知情，测试结束按约定删除不需要的原始音频；不要上传原始录音到 Jev。

按**录制人或录制场次**划分 dev/test，例如 70%/30%。同一段录音及其改写不能分到两边。dev 用于改提示词、设备别名和阈值；test 在调整完成前封存。每次改动把旧 test 结果保留为版本记录，不能边看最终 test 边反复调参。

## 5. 三种跑法，定位错误在哪

### A. Jev 文字回归

给测试程序喂 `reference_text + App 实际可获得的 context`，调用与 App 相同的两阶段问题和候选目录，不调用 ASR。记录第一阶段完整答案、第二阶段答案、置信度、最终校验结果、耗时、调用次数和费用。模型版本、提示词版本、注册表版本和阈值必须一起保存。

### B. 音频端到端回归

将录音经目标手机的实际采集/VAD/ASR 流程输入，在 observe 模式运行，保存 VAD 边界、partial、final 和最终计划。不要用人工转写替换 ASR 结果。对同一 ID 记录 A/B 两条结果：A 对、B 错多半是 VAD/ASR/分段问题；A 和 B 都错则看 Jev、候选与校验。

### C. 连续环境回放

按原时间顺序回放整段录音，保持静音间隔和交叠说话，不把切好的单句当作连续测试。计算每小时误介入、误计划、误执行以及漏掉的真实指令。先 observe 统计“本会执行什么”；只有误计划达到接受条件，才对低风险设备做 live 验证。

### D. ASR 错误转写注入

读取 [ASR 误识别 JSONL](../testdata/asr-misrecognition-v1.jsonl)，将 `asr_text` 直接作为 ASR final transcript 提交给 Jev，逐字段比较 `expected_decision`、`target_id`、`action` 和 `parameters`。该测试隔离了 ASR 输出错误后 Jev 是否仍能恢复意图；它不测 ASR 自己是否会产出指定错误。需要测真实音频链路时，另用 `tts_text` 合成音频并运行实际 ASR，同时保存它真实输出的 transcript。

## 6. 评分表

| 指标 | 分子 / 分母 | 为什么单独看 |
| --- | --- | --- |
| 介入精确率 | 正确处理的请求 / 所有被系统处理的话语 | 插话是否多 |
| 介入召回率 | 被正确处理的请求 / 所有真实请求 | 是否漏听 |
| 非指令误介入率 | 被错误处理的非指令 / 全部非指令 | 排除误唤醒 |
| 每小时误执行计划 | 环境集错误生成的可执行计划 / 小时 | 无唤醒词最关键指标 |
| 业务分类准确率 | 业务正确的已介入样本 / 应介入样本 | Jev 第一阶段 |
| 完整计划准确率 | 目标集合、动作、参数全部正确的样本 / 应执行样本 | 第二阶段最终质量 |
| 危险错误数 | 错设备、反向动作、越界或不应执行却执行的次数 | 不能被平均分掩盖 |
| VAD 漏检/分段错 | 各类错误片段数 / 真实语音段数 | 与 Jev 错误分离 |
| 识别错误率 | 中文可用 CER，或按约定分词的 WER | 只作诊断，不能代替计划准确率 |
| ASR 错误转写计划准确率 | 完整恢复原计划的误识别样本 / 全部误识别样本 | 衡量同音/近音错字是否造成漏执行、错设备、反向动作或错参数 |
| 延迟/费用 | 说完到计划、Jev 调用数与实际成本 | 体验与运行预算 |

统计计划时按结构化内容比较，设备组比较完整集合，数值比较标准单位和值；界面文案措辞不计入计划准确率。`ignore` 与 `needs_input` 都没有副作用，但要分开统计。对“灯开了”与“灯关了”的反向动作、高风险目标、电视声误执行建立独立失败清单。

中文 ASR 可用字符错误率 CER 作为统一口径，但先规定标点、繁简、数字和空格归一化规则；不要通过过度归一化把“开/关”“二十/十二”等关键错误抹掉。通用 WER 定义见 [NIST 说明](https://trec.nist.gov/pubs/trec9/sdrt9_slides/tsld017.htm)。超出支持范围的难例需要专门测，不能只堆常见命令；任务型对话评测对此也有实证讨论。[CLINC OOS 论文](https://aclanthology.org/D19-1131.pdf)

## 7. 建议迭代门槛

第一轮先把明显缺陷找全，不急着宣传单一“准确率”。观察模式的进入 live 条件建议为：封存测试集上明确指令完整计划正确率目标 ≥95%；连续环境至少 8 小时无错误可执行计划；任何错设备、开关反向、电视声导致的执行计划必须逐条修复并重新测试。0 次观测不代表真实误触发概率为 0。

上线低风险设备后保持影子记录：用户纠正、取消、设备状态与计划不一致都作为新回归样本，并注明来源。新增失败样本先进入 dev，留一部分新录制场次作为下一版封存 test，避免对一套题记忆化。

## 8. 最小实施顺序

1. 固定标注规范和设备注册表版本，先用 [初始样例](../testdata/voice-cases-starter.jsonl) 跑通自动比较。
2. 录制第一批约 100 条，补齐人工转写和双人核对的高风险标签。
3. 扩至约 500 条并划分 dev/test，再收连续环境音。
4. 同时运行文字回归、音频端到端和环境回放；输出逐类别混淆表、错例及调用成本。
5. 只在 dev 上调整提示词、阈值、别名和 ASR；封存 test 用于阶段验收。

样例文件是**格式与覆盖面起点**，其中设备逻辑 ID 仍是设计值，且未附真实录音；不能将其成绩当作真机可靠性结论。
